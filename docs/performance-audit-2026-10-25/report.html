FLICK · AUDIT FIRST · 25 OCT 2026 · TWO CLAUDE REVIEWS

The strongest 10× opportunity is eliminating repeated library work.

Start with indexed library state, background settings saves and virtualized views. Fix deletion in the same state model. Playback, PiP, startup, downloads, caches and shutdown also have concrete opportunities below.

No application behavior has changed. A whole-app 10× speedup has not been measured. This report separates source facts, isolated experiments and proposed acceptance goals.

Three optimized helper runs on a busy 4-vCPU Linux VM. Library and history each contain the selected number of generated records. The lookup model follows duration/resume/watched/poster branches without formatting, text layout or GPU work. The prototype is equivalent for this local-file fixture; it is not a complete implementation for torrent identity, UI state or persistence.

What this changes in the diagnosis: repeated library lookups scale much worse than the measured settings save. Both belong off the Back critical path, but a save-only fix would leave the large-library bottleneck.

Deletion bug confirmed in the running app

A generated video was deleted from disk. Its card stayed visible after navigating to All Videos, and the context menu had no Delete action. A Store save/reload experiment also kept the missing file and re-added an entry removed only from the library, because history repopulates it.

Proposed behavior: a visible Delete / Move to Trash button plus a separate Remove from Library action; immediate coherent UI updates; background detection of externally deleted files; durable protection against history and late completion events bringing entries back. Offline drives remain distinguishable from confirmed deletions.

P0Navigation & settingsBack waits for durable disk writes

Before switching views, Back runs persist(), then pause with a second full player snapshot. Each snapshot performs 13 synchronous property reads. save_to clones and sanitizes the entire settings object, serializes it, writes a temporary file, fsyncs and renames it.

src/ui.rs:638, 1071, 1139 · src/store.rs:548 · src/playback.rs:719

Proposed change. Use cached player state for an immediate view transition; queue ordered pause/save work. Add a single coalescing writer with generation ordering, atomic replacement, write-error reporting and a shutdown flush. Never move the existing !Send Player into arbitrary background tasks.

Check. Instrument click → first painted library frame, save subspans and p95/p99 frame gaps. Test newest-save-wins, atomic replacement, quit flush, PiP and resume.

Confirmed code; Back end-to-end latency remains unmeasured.

P0Library & local searchQuadratic metadata work on every rebuild

watched(), resume_position(), video_detail() and poster() repeatedly search library/history vectors. Continue Watching also scans history through resume_position. All Videos, History and Shows build their full item trees; Home scans all entries even though it only displays a few.

src/store.rs:260, 341, 383 · src/library_ui.rs:1036, 1440, 1574, 1818 · src/chrome_ui.rs:103

Proposed change. Maintain path/history/torrent identity indexes and precomputed lowercase titles; cache filtered/sorted data by revision. Stop Home iterators once enough visible matches are found. Virtualize lists and grid rows with stable IDs, keyboard focus and scroll restoration.

Check. Release builds with 100/1k/5k/10k entries: typing latency, Back-to-paint, scroll frame time, RSS and cold/warm image loads.

Measured source-helper bottleneck; prototype is fixture-specific, not a shipped app speedup.

P0Deletion correctnessDeleted files stay visible and records can reappear

The displayed library comes from settings and has no file-deletion watcher/reconciliation. The context menu lacks Delete. sanitize() repopulates library from history, periodic remember() can re-add the open file, and completion events can re-add removed paths.

src/store.rs:177, 196, 433 · src/library_ui.rs:159, 1123 · src/ui.rs:1046

Proposed change. Add visible Delete/Move to Trash and Remove from Library actions, with coherent library/history/torrent updates and entry generations or durable removal markers. Reconcile external deletions off the UI thread on focus/startup and through coalesced file events. Treat offline volumes and permission errors separately from a confirmed deletion.

Check. Delete while playing, from each view and externally; restart; late thumbnail/download events; restored file; offline volume; failed deletion. Verify no resurrection and no UI filesystem scan.

Reproduced interactively and with actual Store save/reload.

P1PiP & render invalidationEvery video frame invalidates the main library

present() calls cx.notify() on the root Flick entity and PiP observes that entity. With PiP active and the library visible, video frame updates rebuild unrelated library content.

src/ui.rs:543, 591, 1661 · src/pip_ui.rs:128

Proposed change. Separate the video frame/surface entity from library, player controls and transfer state. Notify only the affected surface; isolate the timeline too if profiling supports it.

Check. Count library renders per second during PiP and compare CPU/RSS at 1k/5k entries. Preserve track, control and pause updates.

P1Memory & video deliveryFull-size frames use an unbounded queue

The background renderer sends fresh BGRA buffers through an unbounded channel; the UI drops older frames only when it runs again. A 3840×2160 frame is 31.6 MiB, so a blocked UI can accumulate substantial data. The last video and hover images remain after Back.

src/playback.rs:895, 1036, 1122 · src/ui.rs:519, 565, 1140

Proposed change. Use a bounded latest-frame mailbox with generation checks and no blocking dependency on the render thread. Explore a small reclaimable buffer pool after confirming GPUI image ownership. Release/idle hidden resources according to Back/Return and PiP behavior.

Check. Stall the UI deliberately; require bounded queued frames, no stale frames, no producer deadlock and stable RSS through repeated open/Back/PiP cycles.

Unbounded capacity confirmed; queue/RSS growth not measured.

P1Idle CPU & background updatesUnchanged state still triggers scans, saves and repaints

tick scans the whole library for posters every 50 ms playing or 150 ms paused. A retained path causes full settings saves every 5 seconds even in the library. Transfer snapshots are sent every 700 ms whether they changed; the seeding-policy loop wakes every 250 ms.

src/ui.rs:815, 892, 1046 · src/services.rs:326, 406 · src/torrent.rs:302

Proposed change. Track dirty state, queue only missing posters when library state changes, cache incomplete-path sets, diff transfer snapshots and route notifications to interested views. Use wake events plus a low-frequency maintenance timer while idle.

Check. After first watch, measure 10 minutes idle with no transfers, paused transfers and PiP. Count saves, wakeups and view renders; target zero unchanged settings writes.

Confirmed cadence and work; sustained idle CPU/power not measured.

P1Startup & opening filesFirst paint and local opening wait on unrelated work

Flick::new initializes libmpv and checks each poster path on the UI thread. open() gates all files on transfers_known; the services worker restores its saved transfer session before entering its command loop. Restored torrent rechecks can also compete for disk/CPU.

src/ui.rs:369, 490, 675 · src/services.rs:300, 330 · src/torrent.rs:1230

Proposed change. Paint the shell first, initialize playback with explicit ownership off the critical UI path, validate posters asynchronously, and classify known local files without waiting for unrelated transfer initialization. Preserve verified-piece reads and rechecks for claimed torrent content.

Check. Cold/warm launch and open-to-first-frame with empty/large libraries and 0/1/10 local saved transfers. Do not assume Session::start awaits every content hash; initialization and checking must be measured separately.

Code gating confirmed; startup impact with saved transfers unmeasured.

P2Playback controls & scrubbingCommands repeatedly fetch all state; drag seeks are exact

P2Posters, previews & cachesOffscreen posters and abandoned decoders retain work

All cards create img(path) requests without an app-supplied bounded image cache. GPUI caches loaded assets; Flick never calls remove_asset. Poster filenames include mtime/size with no quota/cleanup. Hover preview keeps its last file/player open and only skips requests before starting decode.

src/chrome_ui.rs:103 · src/thumbnails.rs:50, 126, 249 · GPUI 0.2.2 app.rs:1997 and elements/img.rs

Proposed change. Prioritize visible posters, bound decoded-image and disk caches, purge replaced/deleted poster artifacts, cancel stale preview work and idle-close preview decoders. Schedule poster extraction to avoid starving playback.

Check. RSS and disk-cache size after thousands of posters, repeated replacements/deletions and long playback; cancel a slow preview/poster and verify bounded shutdown.

Code/cache ownership confirmed; memory totals and cache hit rates unmeasured.

P2HTTP downloads & transfer snapshotsResume rereads data even when no hash is needed

Part::open reads a partial file to EOF even when hash=false; it could use metadata length and seek. Hashing existing copies and rebuilding required checksums lack cancellation inside the read loop. Transfer snapshots repeatedly clone paths and check selected files through vector membership.

src/fetch/http.rs:125, 376, 400 · src/torrent.rs:558, 581 · src/services.rs:406

Proposed change. Use metadata length for checksum-free resume, retain hashing when required, add cancellation checkpoints, diff/reuse immutable transfer metadata and use selection sets. Consider bounded multi-file concurrency only after measuring disk and server limits.

Check. Generated partial files and loopback HTTP; explicit loopback torrent peers only. Measure resume setup separately from throughput, cancellation and integrity. Never disable checksums/rechecks or promise a faster external network.

Unnecessary read confirmed; download/transfer throughput not benchmarked.

P2Rendering architecture & shutdownSoftware rendering and blocking worker joins need separate work

Software output scales/composes at physical target resolution, allocates each frame and sets alpha; GPUI then uploads it. Drop implementations join preview, poster, renderer and service threads, while inner operations can wait for decode/I/O deadlines.

src/playback.rs:578, 1122, 1177, 1237 · src/thumbnails.rs:96, 183 · src/services.rs:284, 563

Proposed change. Profile decode/scale/upload independently; preserve resolution, color and subtitle sharpness. Benchmark safe copy/alpha fusion and buffer reuse. Prototype native GPU integration separately because current GPUI interop is limited. Add cooperative cancellation and a bounded shutdown protocol.

Check. Release 1080p/4K hardware runs, frame-time distributions, dropped frames, paused CPU and power; quit during slow reads/preview/download. No GPU or zero-copy speedup is claimed here.

Architecture/lifecycle confirmed; device-specific render and shutdown gains unmeasured.

Recommended implementation order

  1. Make actions responsive and state coherent.Add Back-to-paint timing, a coalescing settings writer, library/history indexes, and deletion reconciliation with the Delete button.
  2. Remove work that grows with the whole library.Virtualize lists and grid rows, cache derived state, isolate PiP/video notifications, bound frame delivery and image caches, and remove idle polling/saves.
  3. Improve the remaining measured paths.Separate startup from transfer restoration, coalesce scrubbing and preview work, remove unnecessary HTTP resume reads, and implement cooperative shutdown.
  4. Profile presentation on real hardware.Measure decoding, scaling, uploads and power before choosing a GPU integration. Preserve output resolution, colors and subtitle sharpness.

Checks, methodology and review corrections

Passed: cargo test --locked --all-targets: 102 passing, 11 opt-in tests ignored. The native real_playback backend test also passed separately with generated local H.264/AAC media. cargo build --locked --bin flick passed as a debug desktop build.

Interactive: opened generated media in the existing debug app, observed the test-pattern image, clicked Back to All Videos, reproduced the stale deleted card and missing Delete action, and quit with exit code zero. This was a small isolated Linux/Xvfb session with null audio; it did not measure Back-to-paint latency or audible synchronization.

Helper benchmark: actual Store and Player source compiled at release opt-level 3 with bin LTO off; release dependencies. Each invocation uses one warmup then 9 save/filter/group rounds, 5 metadata/history/prototype rounds, 100 snapshots and 40 double pause-toggle/snapshot rounds. Numeric ranges are the three runs’ medians. The prototype asserts resume/watched/poster equivalence for every fixture entry. The raw results, harness and reproducer accompany this report.

Native helper timing: a playing snapshot median was 0.119–0.124 ms across runs; player initialization 154–334 ms; load to first 1080p software frame received 171–456 ms. These are backend timings under shared host load, not app launch or visible presentation latency. Snapshot reads were much cheaper than large-library lookups on this fixture.

Limits: the VM had unrelated CPU activity (load 9.1–9.2 one-minute load on four CPUs); these are diagnostic helper timings, not hardware acceptance or end-to-end speedups. No new sustained 4K, public-network throughput, multi-GB transfer restart, PiP CPU, power or memory-soak benchmark is claimed. Transfer tests used generated fixtures and explicit local peers; playback measurements were separate.

Claude consultation: two read-only reviews by Claude Opus 5.5 covered Back and then the whole app/deletion. Their observations were checked against source. A snapshot has 13 reads, not the approximate 14 initially reported. librqbit session startup schedules torrent initialization; it is not established that it waits for every content hash. The rgb0 shortcut does not solve GPUI’s BGRA/alpha contract, a default source-resolution cap risks subtitle/quality regressions, and GPU zero-copy requires separate interop research.

mpv itself documents that synchronous calls can wait for the playback core and that asynchronous calls need completion ordering: mpv 0.37 client API. Its render API also requires careful thread separation: mpv 0.37 render API.
